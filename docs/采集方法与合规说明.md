记录这套数据是怎么拿到的、为什么不爬、中间踩了哪些坑，以及它们如何反过来成为作品的一部分。

## 一、为什么不写爬虫

> 这一节我改过。**第一版只写了「平台禁止 + 有反爬，所以不爬」，这个论证是偷懒的**——
> 「我又不用于商业」这个反问完全成立，而当时我没能正面回答它。下面换成基于条文和判例的版本。

### 1.1 先把「非商业用途能不能免责」说清楚

**答案：这是一个真实存在的辩护理由，但不足以单独免责。**

中央网信办《网络爬虫的法律规制》一文，专门列举了爬虫使用者的常见辩护话术，其中就包括
**「这些数据我只是个人研究使用，并没有商业目的」**，并指出：

> 「依托行为是否具有恶意或者通过主观层面来判断爬虫行为违法与否是具有难度的……
> 对网络爬虫进行规制应当基于**客观结果**，即是否妨碍网站的正常运行或者对他人合法权益造成严重危害。」

也就是说：**「不商用」会被考虑，但决定性的不是你的目的，而是你的客观行为后果。**
用它当挡箭牌是不牢靠的，但它确实不是无效辩护。

### 1.2 刑事风险的关键分界：突破的是「身份认证」还是「访问方式」

这一点是本项目判断的核心，也是最容易被误传的地方。

《刑法》第 285 条非法获取计算机信息系统数据罪，构成要件中的「未经授权」，
**司法上核心判断的是「是否突破以身份认证为核心的访问控制机制」，而不是「是否规避了反爬措施」**。

- **反爬措施**（User-Agent 识别、IP 频率限制、验证码）本质是**「访问方式限制」**，
  目的是防止服务器过载，并不剥夺访问权限。规避它们，通常不构成刑法意义上的「突破安全保护措施」。
- **身份验证机制**（账号密码、短信验证码、生物识别、设备绑定）才是**「访问权限限制」**。
  突破它去抓取本不该看到的数据，才触及刑事红线。

最高人民检察院的表述也印证了这个分界：

> 「如果爬取**互联网公开的普通数据，原则上不构成犯罪**，因为公开数据忍受爬取也是互联网互联互通本质的体现。」

**推论**：低频、小量地抓取 BOSS 直聘**无需登录即可公开访问**的 JD，且不干扰平台运行 ——
按这个标准，刑事风险是**低**的。这是我第一版没说清、也不该含糊过去的地方。

### 1.3 那真正的红线在哪？三条，每条都有判例

风险不在「爬」这个动作本身，而在下面这三种**升级行为**：

| 红线 | 为什么危险 | 判例 / 依据 |
|---|---|---|
| **① 突破登录态抓非公开内容** | 触及 285 条的「身份认证」核心。BOSS 直聘的**完整 JD 与沟通功能需要登录**，用技术手段绕过后抓取，性质就从「抓公开数据」变成「越权获取」 | 上海 Z 公司案：绕开 IP 限制、验证码抓取外卖平台数据 → 非法获取计算机信息系统数据罪 |
| **② 公开发布爬虫工具/插件** | **这是学生最容易踩、也最贴近我们情形的一条。** 不需要大量数据、不需要牟利，发布即可能构成「提供侵入、非法控制计算机信息系统程序、工具」 | 许某案：在 GitHub 发布「推特媒体爬虫」插件，获利仅 **1.3 万元** → 依据《网络安全法》第 27、63 条，**没收违法所得 + 行政拘留三日** |
| **③ 高频大量抓取，干扰平台运行** | 可能因「干扰计算机信息系统正常运行」构成破坏计算机信息系统罪 | 广州青虎浏览器案：爬取电商数据 6700 万条 → 罚款 10 万元；最高检：爬虫过快或大量重复访问、后果严重的可构罪 |

补充一条被忽略的：**反不正当竞争法第 12 条的主体是「经营者」**。
个人学习用途、不与平台构成竞争关系，严格来说不适用这一条 —— 所以**民事赔偿的风险对本项目近乎为零**。

### 1.4 既然风险不大，为什么还是没爬

不是因为「怕被抓」，而是**这三笔账算下来不划算**：

1. **收益极小。** 补到能让 Python 结论显著，只需要 **13 张截图 ≈ 10 分钟**。
   用任何非零风险去换 10 分钟，不划算 —— 这是真正的理由。
2. **风险不是零，且性质特殊。** 许某案说明：即使只发了个小插件、获利一万出头，也可能落行政处罚。
   我走 ACS + 澳洲 EOI 路径，**需要开具无犯罪记录证明**。
   行政拘留属行政处罚、理论上不进入犯罪记录，但一旦情节被认定升级为刑事，
   代价是**整条移民路径** —— 这是典型的**收益风险不对称**。
3. **最重要的一条：爬了，这份作品最值钱的东西就没了。**
   面试官看作品集，看到「我爬了 1000 条」的第一反应是**合规意识存疑**，
   看到「我说清了数据来源与边界、且敢写清局限」的反应是**这人有判断力**。
   **「我选择不爬，并且能说清为什么不爬」本身就是这条作品的卖点** ——
   这个卖点价值 1000 条数据，而且它不产出于法律，产出于你的判断。

> 一句话总结：**不是不能，是不值。**

## 二、最终采用的采集方式

**人工浏览 + 手机截图 + 本地 OCR** —— 采集速度完全等于人工翻页速度，不发任何网络请求、不批量请求、不绕过验证。本质上只是省掉了「复制粘贴」。

```
手机端浏览 BOSS 直聘「数据分析」搜索结果
  → 每条进详情页，一张截全（标题 + 薪资 + 学历经验 + 职位描述）
  → 长 JD 分屏截（同一 JD 可能占 2–4 张）
  → 传到电脑，全丢进 data/screenshots/
  → 本地 OCR 批量识别
```

采集量：154 张截图（含续屏）→ 归并后 118 个 JD → 剔除 1 张非 JD 图 → 与已有 31 条跨批去重剔除 14 条 → **净新增 103 条，总计 134 条**。

## 三、踩过的坑（按严重程度排序）

### 坑 1：跨批去重不能用文本相似度

已有 31 条是人工整理过的**精简文本**，OCR 批次是**带手机状态栏、地图小区名的原始噪音文本**。两者字面差异极大，4-gram Jaccard 相似度只有 0.1–0.3，**自动去重只抓到 1 条重复**（实际有 14 条）。

改用「公司名核心词 + 薪资 + 正文」三重判据后抓到 18 条，但其中 **7 条是误判** —— 正则把地图上的银行名当成了公司名（如「中国工商银行」出现在职位地址附近）。

**最终处理**：逐条打开正文人工核验，14 条确认重复剔除、7 条保留。这一步无法自动化，是整套流程里最耗时但最必要的部分。

### 坑 2：OCR 错字是系统性的

RapidOCR 识别中文 JD 的正文准确率很高，但存在**固定错字**：

- 「职位详情」→「职位洋情」（几乎每处都错）
- 「天猫」→「天猎」
- 城市名偶发误识（「苏州」→「荔州」）

**影响**：关键词匹配不受影响（技能词都是英文或常见中文词），但**城市切片会算错**，必须后处理修正（已用规则 + 人工核对修正）。

### 坑 3：城市混杂

前 31 条清一色太原，OCR 批次混进了杭州(26)/上海(22)/北京(14)。最初想混在一起算，但**太原 5.5K vs 一线 14.5K，混算的薪资中位数毫无意义**。

**处理**：改为分城市切片。巧合的是太原和一线各 66 条，样本天然对称，对比结论反而比原计划的单一城市分析更有说服力。

### 坑 4：判定标准定错了，会系统性误判一整类岗位

「标题党」的初版规则是「正文无技术技能 + 话术特征」。按这个规则，字节跳动经营分析岗（35-45K·15薪）、华为销售分析岗（10-15K·14薪）、某电商数据运营岗全被判成标题党 —— 因为它们**JD 通篇不写工具名**。

**问题**：这三条都有真实、具体的业务职责，不是挂羊头。把它们算成标题党，报告还会自相矛盾（4.5 节的洞察拿字节那条当"真岗"讲，统计里却算成了标题党）。

**修正**：把判定标准从「是否提到工具名」改成「**是否挂羊头**」—— 即标题写数据岗、实际招的却不是数据岗。据此把 3 条改判为真岗，标题党从 20 条降到 17 条（13%）。

**教训**：规则引擎的判定标准必须和结论里的定义保持一致，否则报告内部会打架。这类"高层岗位不谈工具"的边界案例，只能靠人工复核兜住。

### 坑 5：平台的技能标签也会骗人

BOSS 会给 JD 打技能标签。一条「数据信息员」标签写着「数据分析/挖掘经验」，正文实际是「把客户信息整理好交给销售部门，学历不限、小白可、一对一指导」。

**结论**：只看平台标签筛岗位不可靠，必须读正文。这条已写进报告正文。

### 坑 6：噪声过滤会把最优质的岗位整批误杀

第二轮补采 200 条时，我用「页面出现『发现』『微信』『BOSS直聘』」当噪声特征，
结果 **22 条真 JD 被剔除**，其中包括拼多多 30-60K、兴业银行太原分行 8-10K。

**原因**：BOSS 的 JD 详情页底部本来就有这些导航/来源文字，它们是页面的一部分，不是噪声。

**修法**：换成更强的判据 —— **有薪资格式（`\d+-\d+K` / `元/天`）= 一定是 JD**，直接放行；
只有无薪资的记录才走噪声判断。改完噪声从 22 条降到 1 条（一个真的英语口语 App 页面）。

> 通用原则：**判断"不是什么"比判断"是什么"危险得多。** 用「像噪声」去删数据前，
> 先问有没有更硬的正面判据可以放行。

### 坑 7：OCR 会系统性错识，且错误是有规律的

不是随机错，是**成体系的错**。第二轮遇到三类，都用「上下文反查」确认了真值：

| OCR 结果 | 真值 | 反查依据 |
|---|---|---|
| 荔州（含"新荔州""析师荔州"） | **苏州** | 地址命中 姑荔区=姑苏区 / 虎丘区 / 吴中区 / 相城区 / 荔州工业园区 |
| 充锡（含"新充锡""程师充锡"） | **无锡** | 地址命中 锡山区 / 梁溪区 / 惠山区 |
| 浑圳 / 深训 | **深圳** | — |
| 职位洋情 | **职位详情** | 每页固定出现，是「职位详情」四字的稳定错识 |

前两类的前缀粘连（"析师荔州"）是**岗位名被并进了城市字段**（"分析师"+"苏州"）。

> 通用原则：**OCR 错字要靠结构化线索反查，不能靠猜。** 中国地址「市·区」这个格式
> 提供了天然的校验位 —— 区名能反推出市名。发现异常城市名时，先看它的区名。

### 坑 8：增量合并时 id 只查一次起点，会与旧批次全量撞号

新增 200 条分配 id 时，我只在最开始查了一次「下一个可用编号」，之后循环里直接 `nxt += 1`
而**没有重新检查是否已占用**。结果从 OCR001 开始重编，与旧批次 103 条**全部撞号**，
334 条里出现 103 个重复 id。

**修法**：每次分配后都把新 id 加入 `used` 集合，下次分配前重新跳过。

> 通用原则：**批量分配唯一标识符时，"查一次起点"是不够的 —— 已用集合必须在每次分配后更新。**

### 坑 9：归并脚本不产出的字段，合并后会让统计失真

`merge_ocr.py` 只做文本归并，**不产出 `skills` 和 `flag`**。新增 200 条带着空字段进了主库，
直接后果是：标题党率从 13% 被稀释到 5.3%，技能榜也失真。

**修法**：在增量合并脚本里统一调用 `parse_jd.py` 补齐 `skills` / `flag` / `reason`，
保证新旧记录字段口径一致。**凡是脚本 A 产出、脚本 B 消费的字段，必须在交接处校验非空。**

## 四、技能归并规则（SKILL_ALIAS）

同一技能在 JD 里有几十种写法，直接词频统计会被拆碎。归并规则在 `scripts/parse_jd.py`：

| 标准技能名 | 归并的写法 |
|---|---|
| SQL | sql / mysql / oracle / 关系型数据库 / postgresql / sql server / 数据库 |
| BI可视化 | tableau / power bi / finebi / 帆软 / 永洪 / smartbi / echarts / 数据可视化 |
| 统计学 | 统计学 / 统计 / 数学·统计 |
| Python | python / pandas / numpy / pyspark |
| Excel | excel / vlookup / 数据透视 |
| 数据挖掘 | 数据挖掘 / 数据分析·挖掘 |
| R / SPSS | r语言 / spss / sas |

**注意**：归并规则由本人定义，换一套规则数字会不同 —— 这一点已写进报告的「局限」部分。

## 五、关于引入的第三方对照数据（必须单独说明）

为了补足「自采单日快照没有时间维度」这一缺陷，本报告 4.6 节引入了一份第三方公开数据集：

| 项 | 内容 |
|---|---|
| 来源 | GitHub 公开仓库 `BigCarrey/Data_analysis_in_lagou` |
| 内容 | 2016-09-06 拉勾网数据分析岗 589 条，含 JD 全文（21 字段） |
| **采集方式** | **第三方于 2016 年使用「集搜客」网络爬虫工具抓取**（原仓库 README 自述） |
| 本人行为 | **仅下载仓库中已公开的 .xlsx 文件做只读分析，未实施、未参与任何抓取** |

### 为什么这不算「我也用了爬虫」

这是本项目最需要说清的一点，否则会与第一章「为什么不写爬虫」自相矛盾：

1. **行为主体不同。** 抓取行为发生在 2016 年，实施者是仓库作者，不是本人。
   本人的行为是「下载一个已公开 9 年的文件并读取」，与「读一篇引用了爬虫数据的论文」性质相同。
2. **平台与对象不同。** 本项目规避的是对 BOSS直聘 的自动化抓取；这份数据的对象是拉勾网，
   且是 9 年前的页面状态。
3. **用途受限。** 它**只做时间趋势的方向性对照，未混入主样本**，128 条的统计口径完全不变。
4. **来源显式标注。** 报告中以独立章节 + 采集方式对比表 + 局限条目三处声明，
   **不冒充自采、不掩盖来源**。

### 附带做的数据核验

下载后我对这份数据做了一次真实性核验，结论是**可用**：

- 按「岗位名 + 公司 + 城市」查重发现 32 组疑似重复（涉及 74 条），
  但**逐条核对正文后发现它们并不相同** —— 是同一家公司投放了多个不同的数据分析岗
  （如美团点评 3 个、北京捷越联合 4 个），属于真实的多岗位，不是重复投放。
- 用「岗位名 + 公司 + 城市 + JD 正文前 200 字」严格去重后，一线样本 518 → 504 条，
  **各项技能占比变化均 < 0.7pp**，不影响任何结论。
- 因此报告直接采用原数据，未做额外剔除。

> 判断标准：**如果核验发现数字会明显改变，就必须改；核验后无影响，就如实说明「已核验、无影响」。**
> 不能用"我做了去重"来暗示做了大修正。

## 六、数据隐私

- `data/screenshots/`（154 张原始截图，98MB）**不入库**：含个人账号昵称、消息、定位等隐私信息
- `data/ocr_text/`（OCR 文本）同样不入库
- 对外只发布结构化结果（`jd_dataset.json` / `.csv`），其中的公司名与岗位描述均为公开招聘信息
