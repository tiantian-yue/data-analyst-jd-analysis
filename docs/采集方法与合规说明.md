# 采集方法与合规说明

记录这套数据是怎么拿到的、为什么不爬、中间踩了哪些坑，以及它们如何反过来成为作品的一部分。

---

## 一、为什么不写爬虫

招聘平台（BOSS 直聘）的用户协议明确禁止自动化抓取，且部署了完整的反爬体系。我实际验证到的有三层：

| 反爬机制 | 表现 | 我的处理 |
|---|---|---|
| **薪资字体加密** | 列表页薪资数字用自定义字体渲染，`Ctrl+A` 复制出来是 `- K`，数字丢失 | 改为从列表页人工回填 |
| **文字防选中** | 详情页 JS 拦截 `selectstart` / `copy`，全选后复制出来是空的 | 改用截图采集 |
| **开发者工具检测** | 按 `F12` 立刻被强制退出页面 | **未绕过**，放弃控制台方案 |

**我的判断**：绕过这些机制属于对抗平台，风险（账号封禁、法务函）落在个人身上，而我需要的只是回答「企业到底要什么技能」—— 人工采集完全够用。

同时，作品集里写「用爬虫抓了 100 条招聘数据」对求职是**减分项**：面试官的第一反应是合规意识存疑、第二反应是数据可信度存疑。把「我说清了数据来源与边界」写进作品，反而更能证明判断力。

## 二、最终采用的采集方式

**人工浏览 + 手机截图 + 本地 OCR** —— 采集速度完全等于人工翻页速度，不发任何网络请求、不批量请求、不绕过验证。本质上只是省掉了「复制粘贴」。

```
手机端浏览 BOSS 直聘「数据分析」搜索结果
  → 每条进详情页，一张截全（标题 + 薪资 + 学历经验 + 职位描述）
  → 长 JD 分屏截（同一 JD 可能占 2–4 张）
  → 传到电脑，全丢进 data/screenshots/
  → 本地 OCR 批量识别
```

采集量：154 张截图（含续屏）→ 归并后 118 个 JD → 剔除 1 张非 JD 图 → 与已有 31 条跨批去重剔除 14 条 → **净新增 103 条，总计 134 条**。

## 三、踩过的坑（按严重程度排序）

### 坑 1：跨批去重不能用文本相似度

已有 31 条是人工整理过的**精简文本**，OCR 批次是**带手机状态栏、地图小区名的原始噪音文本**。两者字面差异极大，4-gram Jaccard 相似度只有 0.1–0.3，**自动去重只抓到 1 条重复**（实际有 14 条）。

改用「公司名核心词 + 薪资 + 正文」三重判据后抓到 18 条，但其中 **7 条是误判** —— 正则把地图上的银行名当成了公司名（如「中国工商银行」出现在职位地址附近）。

**最终处理**：逐条打开正文人工核验，14 条确认重复剔除、7 条保留。这一步无法自动化，是整套流程里最耗时但最必要的部分。

### 坑 2：OCR 错字是系统性的

RapidOCR 识别中文 JD 的正文准确率很高，但存在**固定错字**：

- 「职位详情」→「职位洋情」（几乎每处都错）
- 「天猫」→「天猎」
- 城市名偶发误识（「苏州」→「荔州」）

**影响**：关键词匹配不受影响（技能词都是英文或常见中文词），但**城市切片会算错**，必须后处理修正（已用规则 + 人工核对修正）。

### 坑 3：城市混杂

前 31 条清一色太原，OCR 批次混进了杭州(26)/上海(22)/北京(14)。最初想混在一起算，但**太原 5.5K vs 一线 14.5K，混算的薪资中位数毫无意义**。

**处理**：改为分城市切片。巧合的是太原和一线各 66 条，样本天然对称，对比结论反而比原计划的单一城市分析更有说服力。

### 坑 4：判定标准定错了，会系统性误判一整类岗位

「标题党」的初版规则是「正文无技术技能 + 话术特征」。按这个规则，字节跳动经营分析岗（35-45K·15薪）、华为销售分析岗（10-15K·14薪）、某电商数据运营岗全被判成标题党 —— 因为它们**JD 通篇不写工具名**。

**问题**：这三条都有真实、具体的业务职责，不是挂羊头。把它们算成标题党，报告还会自相矛盾（4.5 节的洞察拿字节那条当"真岗"讲，统计里却算成了标题党）。

**修正**：把判定标准从「是否提到工具名」改成「**是否挂羊头**」—— 即标题写数据岗、实际招的却不是数据岗。据此把 3 条改判为真岗，标题党从 20 条降到 17 条（13%）。

**教训**：规则引擎的判定标准必须和结论里的定义保持一致，否则报告内部会打架。这类"高层岗位不谈工具"的边界案例，只能靠人工复核兜住。

### 坑 5：平台的技能标签也会骗人

BOSS 会给 JD 打技能标签。一条「数据信息员」标签写着「数据分析/挖掘经验」，正文实际是「把客户信息整理好交给销售部门，学历不限、小白可、一对一指导」。

**结论**：只看平台标签筛岗位不可靠，必须读正文。这条已写进报告正文。

## 四、技能归并规则（SKILL_ALIAS）

同一技能在 JD 里有几十种写法，直接词频统计会被拆碎。归并规则在 `scripts/parse_jd.py`：

| 标准技能名 | 归并的写法 |
|---|---|
| SQL | sql / mysql / oracle / 关系型数据库 / postgresql / sql server / 数据库 |
| BI可视化 | tableau / power bi / finebi / 帆软 / 永洪 / smartbi / echarts / 数据可视化 |
| 统计学 | 统计学 / 统计 / 数学·统计 |
| Python | python / pandas / numpy / pyspark |
| Excel | excel / vlookup / 数据透视 |
| 数据挖掘 | 数据挖掘 / 数据分析·挖掘 |
| R / SPSS | r语言 / spss / sas |

**注意**：归并规则由本人定义，换一套规则数字会不同 —— 这一点已写进报告的「局限」部分。

## 五、关于引入的第三方对照数据（必须单独说明）

为了补足「自采单日快照没有时间维度」这一缺陷，本报告 4.6 节引入了一份第三方公开数据集：

| 项 | 内容 |
|---|---|
| 来源 | GitHub 公开仓库 `BigCarrey/Data_analysis_in_lagou` |
| 内容 | 2016-09-06 拉勾网数据分析岗 589 条，含 JD 全文（21 字段） |
| **采集方式** | **第三方于 2016 年使用「集搜客」网络爬虫工具抓取**（原仓库 README 自述） |
| 本人行为 | **仅下载仓库中已公开的 .xlsx 文件做只读分析，未实施、未参与任何抓取** |

### 为什么这不算「我也用了爬虫」

这是本项目最需要说清的一点，否则会与第一章「为什么不写爬虫」自相矛盾：

1. **行为主体不同。** 抓取行为发生在 2016 年，实施者是仓库作者，不是本人。
   本人的行为是「下载一个已公开 9 年的文件并读取」，与「读一篇引用了爬虫数据的论文」性质相同。
2. **平台与对象不同。** 本项目规避的是对 BOSS直聘 的自动化抓取；这份数据的对象是拉勾网，
   且是 9 年前的页面状态。
3. **用途受限。** 它**只做时间趋势的方向性对照，未混入主样本**，128 条的统计口径完全不变。
4. **来源显式标注。** 报告中以独立章节 + 采集方式对比表 + 局限条目三处声明，
   **不冒充自采、不掩盖来源**。

### 附带做的数据核验

下载后我对这份数据做了一次真实性核验，结论是**可用**：

- 按「岗位名 + 公司 + 城市」查重发现 32 组疑似重复（涉及 74 条），
  但**逐条核对正文后发现它们并不相同** —— 是同一家公司投放了多个不同的数据分析岗
  （如美团点评 3 个、北京捷越联合 4 个），属于真实的多岗位，不是重复投放。
- 用「岗位名 + 公司 + 城市 + JD 正文前 200 字」严格去重后，一线样本 518 → 504 条，
  **各项技能占比变化均 < 0.7pp**，不影响任何结论。
- 因此报告直接采用原数据，未做额外剔除。

> 判断标准：**如果核验发现数字会明显改变，就必须改；核验后无影响，就如实说明「已核验、无影响」。**
> 不能用"我做了去重"来暗示做了大修正。

## 六、数据隐私

- `data/screenshots/`（154 张原始截图，98MB）**不入库**：含个人账号昵称、消息、定位等隐私信息
- `data/ocr_text/`（OCR 文本）同样不入库
- 对外只发布结构化结果（`jd_dataset.json` / `.csv`），其中的公司名与岗位描述均为公开招聘信息
