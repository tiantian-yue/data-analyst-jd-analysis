② 第 1 周 · 窗口函数（3 篇笔记转绿）

核心：三个排名函数的区别 / 每组 TopN / LAG-LEAD / 累计与移动窗口第 1–5 天
D1三个排名函数到底差在哪employee 表 · 60′
  • 写一条 SQL，同时输出 ROW_NUMBER / RANK / DENSE_RANK 三列，按部门分组、薪资降序
  • 盯着技术部李四和王五（都是 18000），口述三列的差别：行号 / 并列跳号 / 并列不跳号
  • 想清楚一件事：如果领导要「每个部门薪资第二高的那个人」，用哪个函数？（先记下你的答案，D2 会打脸 —— 技术部李四和王五并列 18000）
参考答案 + 实测结果
SELECT name, dept, salary,
       ROW_NUMBER() OVER (PARTITION BY dept ORDER BY salary DESC) rn,
       RANK()       OVER (PARTITION BY dept ORDER BY salary DESC) rk,
       DENSE_RANK() OVER (PARTITION BY dept ORDER BY salary DESC) dr
FROM employee ORDER BY dept, rn;
张三 技术 20000  rn=1 rk=1 dr=1
李四 技术 18000  rn=2 rk=2 dr=2
王五 技术 18000  rn=3 rk=2 dr=2   <-- 关键行
赵六 销售 15000  rn=1 rk=1 dr=1
钱七 销售 12000  rn=2 rk=2 dr=2

李四和王五并列 18000：ROW_NUMBER 硬给 2 和 3（并列也被拆开）；RANK 都给 2，下一个直接跳到 4；DENSE_RANK 都给 2，下一个还是 3。

D2每组取 Top1 —— D1 的答案在这里被推翻score + employee 表 · 60′
  • 查「每门课的最高分是谁」：ROW_NUMBER() = 1 包一层外层查询
  • 再查「每个部门薪资第二高的人」—— 技术部李四和王五并列 18000，你用 rn = 2 只会出李四，王五被丢掉了。改用 rk = 2 再试，两个人都会出来
  • 把结论写进笔记：要「只取一条」用 ROW_NUMBER，要「并列全保留」用 RANK。需求不同，函数不同。
  • 顺带把 03-聚合与分组/每组取最大值.md 也过一遍——它有不用窗口函数的写法，对比一下哪种更好读
参考答案 + 实测结果
SELECT * FROM (
  SELECT cname, sid, grade,
         ROW_NUMBER() OVER (PARTITION BY cname ORDER BY grade DESC) rn
  FROM score
) t WHERE rn = 1;
SQL实践  1号  92
数据库   4号  95
-- 换成「每个部门薪资第二高的人」，差别立刻显形：
WHERE rn = 2  →  技术部只出李四（18000），王五被丢掉
WHERE rk = 2  →  技术部出李四 + 王五（两人并列 18000）  <-- 这个才是对的

王五和李四薪资完全相同，凭什么留一个丢一个？需求说「第二高的人」时，并列必须都算。 但反过来，如果需求是「给每个部门第二高的人发一份奖金（一人一份）」，那就必须用 ROW_NUMBER 只挑一个 —— 需求不同，函数不同，没有哪个更好。

D3LAG / LEAD 算日活环比，撞上断档坑events 表 · 60′
  • 先按天聚合日活：SELECT event_date, COUNT(DISTINCT user_id) FROM events GROUP BY event_date
  • 用 LAG 加一列「昨日 UV」和一列「环比差」
  • 再加一列：DATEDIFF(event_date, LAG(event_date) OVER (ORDER BY event_date)) —— 看看哪一天不是 1
  • 你会发现 09-14 那行这个值是 3。说明「昨日 UV」那一列在 09-14 其实是 09-11 的数。先记住这个现象，别修，第 3 周修。
参考答案 + 实测结果
WITH dau AS (
  SELECT event_date, COUNT(DISTINCT user_id) uv FROM events GROUP BY event_date
)
SELECT event_date, uv,
       LAG(uv) OVER (ORDER BY event_date) AS 昨日,
       uv - LAG(uv) OVER (ORDER BY event_date) AS 环比差,
       DATEDIFF(event_date, LAG(event_date) OVER (ORDER BY event_date)) AS 与上行的天数差
FROM dau ORDER BY event_date;
09-10  6   5   +1   1
09-11  6   6    0   1
09-14  7   6   +1   3   <-- 断档：09-12、09-13 没有数据
09-15  8   7   +1   1

LAG 取的是「上一行」，不是「昨天」。数据缺行时它照样返回上一行的值，环比就这么算错了。

D4累计求和与移动平均events + employee 表 · 60′
  • 日活表上加两列：累计 UV（SUM() OVER (ORDER BY ...)）和 7 日移动平均（ROWS BETWEEN 6 PRECEDING AND CURRENT ROW）
  • 拿 employee 表做组内累计，你会看到一个怪事：技术部李四和王五的「累计」都是 56000，不是逐行增加 —— 想明白为什么（提示：并列值时默认按 RANGE 一次算完）
  • 想逐行累加怎么办？ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
参考答案 + 实测结果
-- 7 日移动平均（日活表）
WITH dau AS (SELECT event_date, COUNT(DISTINCT user_id) uv FROM events GROUP BY event_date)
SELECT event_date, uv,
       ROUND(AVG(uv) OVER (ORDER BY event_date ROWS BETWEEN 6 PRECEDING AND CURRENT ROW), 2) AS 近7日均
FROM dau ORDER BY event_date;
-- employee 组内累计：并列值的两种写法
SELECT name, salary,
       SUM(salary) OVER (PARTITION BY dept ORDER BY salary DESC) AS 默认写法,
       SUM(salary) OVER (PARTITION BY dept ORDER BY salary DESC
                         ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) AS 逐行写法
FROM employee WHERE dept='技术';
张三 20000  20000  20000
李四 18000  56000  38000
王五 18000  56000  56000   <-- 默认写法把并列的两个一起加完

D6用 WITH 把嵌套查询拆平events 表 · 60′

  • 再用 WITH dau AS (...), avg_dau AS (...) 重写一遍，对比可读性
  • 结论写进 05-子查询与CTE/CTE与WITH.md：CTE 不改变性能，改变的是「三个月后你还看得懂吗」

参考答案
WITH dau AS (
  SELECT event_date, COUNT(DISTINCT user_id) uv FROM events GROUP BY event_date
), avg_dau AS (
  SELECT AVG(uv) m FROM dau
)
SELECT d.event_date, d.uv, ROUND(a.m,2) 月均
FROM dau d CROSS JOIN avg_dau a
WHERE d.uv > a.m ORDER BY d.event_date;
-- 递归 CTE 预热（第 3 周造日期维表要用）
WITH RECURSIVE seq AS (
  SELECT 1 n UNION ALL SELECT n+1 FROM seq WHERE n < 10
) SELECT * FROM seq;
D7自连接算次日留存（本周核心题）users + events · 75′
  • 用 users JOIN events 找「注册当天活跃过的人」，再 LEFT JOIN events 找「第二天也来了的人」
  • 连接条件怎么写？a.event_date = u.reg_date + INTERVAL 1 DAY —— 日期加减是这题的命门
  • 算出次日留存率，然后回头手算校验：1–6 号和 13–18 号应该留下，7–12 号不该留下
参考答案 + 实测结果
SELECT COUNT(DISTINCT u.user_id) AS 当日活跃,
       COUNT(DISTINCT a.user_id) AS 次日回访,
       ROUND(100*COUNT(DISTINCT a.user_id)/COUNT(DISTINCT u.user_id),1) AS 次日留存率
FROM users u
JOIN events e ON e.user_id = u.user_id AND e.event_date = u.reg_date
LEFT JOIN events a ON a.user_id = u.user_id
                  AND a.event_date = u.reg_date + INTERVAL 1 DAY;
当日活跃 16 | 次日回访 11 | 68.8

注意：换一种口径结果就变了 —— 按「首次活跃日」算是 17 / 11 / 64.7%。 差异来自 12 号和 13 号：他们撞上了 09-12、09-13 的埋点故障，注册当天根本没有数据， 按注册日算会被直接踢出分母（分母 18→16），按首次活跃日算则会被记成「09-14 才首次活跃」。 两种口径都能用，但简历和面试时必须说清你用的是哪一种 —— 说不清口径，等于没做。 顺手把 02-多表JOIN 里的 ON与WHERE的区别.md 翻出来看：把留存条件写进 WHERE 会怎样？（LEFT JOIN 退化成 INNER JOIN，僵尸号消失）

D8找「从来没出现过的人」+ NOT IN 的 NULL 坑users + events + course · 60′
  • 查僵尸号：注册后一条行为都没有的用户（答案应该是 19–24 号，6 个人）
  • 分别用 LEFT JOIN ... IS NULL 和 NOT IN (子查询) 两种写法，对比结果是否一致
  • 再用 course 表练一次「哪些课没人考」（答案是 Python基础）—— 回忆为什么 NOT IN 遇到 NULL 会返回空集
参考答案 + 实测结果
SELECT u.user_id, u.reg_date
FROM users u LEFT JOIN events e ON e.user_id = u.user_id
WHERE e.user_id IS NULL ORDER BY u.user_id;
19 号 09-19 / 20 号 09-20 / 21 号 09-21 / 22 号 09-22 / 23 号 09-23 / 24 号 09-24

6 个僵尸号。用 NOT IN 也能得到同样结果——但前提是子查询里的 user_id 没有 NULL。 只要子查询返回的结果集里含一个 NULL，NOT IN 就会整体返回空。这是 LEFT JOIN IS NULL 更稳的原因。

D9漏斗转化 + 撞上乱序坑events 表 · 60′
  • 算四层漏斗 UV：visit → view → cart → pay（先按 user_id 去重，否则 1 号那条重复的 visit 会污染结果）
  • 输出每层的转化率和整体支付率
  • 然后处理坑②：2 号有 cart 却没有 view。业务上这不合理，你的漏斗要怎么处理它？ 两种思路都写一版：宽松版（不校验顺序，各层独立计数）和 严格版（必须前一层的日期 ≤ 后一层才计入）
参考答案 + 实测结果
-- 宽松版（各层独立去重计数）
SELECT SUM(event_type='visit') 访问, SUM(event_type='view') 浏览,
       SUM(event_type='cart')  加购, SUM(event_type='pay')   支付,
       ROUND(100*SUM(event_type='pay')/SUM(event_type='visit'),1) 整体支付率
FROM (SELECT DISTINCT user_id, event_type FROM events) t;
访问 17 | 浏览 15 | 加购 8 | 支付 3 | 整体支付率 17.6

严格版要先按 user 取出「首次 view 日期」和「首次 cart 日期」，再要求 cart日期 >= view日期 才计入—— 2 号会被剔除。真实业务里两种口径都会遇到，关键是你要能说清自己用的是哪种。

D11模板一：留存（一次输出次日 / 7 日 / 30 日）events · 75′
  • 关键点：先把 events 去重成「用户 × 日期」（SELECT DISTINCT），后面全部基于它算
  • 取每个用户的首次活跃日，然后 LEFT JOIN 三次（+1 天 / +7 天 / +30 天），用 COUNT(DISTINCT CASE WHEN ...) 一次算完三列
  • 再按注册渠道分组看留存差异 —— 这一步做完，它就能写进简历了
参考答案 + 实测结果
WITH act AS (SELECT DISTINCT user_id, event_date FROM events),
fd AS (SELECT user_id, MIN(event_date) fd FROM act GROUP BY user_id)
SELECT COUNT(DISTINCT f.user_id) 首日活跃,
       COUNT(DISTINCT CASE WHEN a1.user_id IS NOT NULL THEN f.user_id END) 次日,
       COUNT(DISTINCT CASE WHEN a7.user_id IS NOT NULL THEN f.user_id END) 七日,
       ROUND(100*COUNT(DISTINCT a1.user_id)/COUNT(DISTINCT f.user_id),1) 次日留存率
FROM fd f
LEFT JOIN act a1 ON a1.user_id=f.user_id AND a1.event_date=f.fd+INTERVAL 1 DAY
LEFT JOIN act a7 ON a7.user_id=f.user_id AND a7.event_date=f.fd+INTERVAL 7 DAY;
首日活跃 17 | 次日 11 | 七日 4 | 次日留存率 64.7
D12模板二：环比 —— 把 D3 的断档坑修掉events · 75′
  • 用 WITH RECURSIVE 造一张 09-01 ~ 09-30 的连续日期表
  • LEFT JOIN 日活表，缺失的日期补 COALESCE(uv, 0)
  • 现在再算 LAG 环比 —— 09-12、09-13 会出现 uv=0，环比是 −7 和 +7，这才是真实情况
  • 这一步是本周最大收获：日期维表是环比/留存类需求的标准前置动作，很多应届生不会
参考答案
WITH RECURSIVE cal AS (
  SELECT DATE('2026-09-01') d
  UNION ALL
  SELECT d + INTERVAL 1 DAY FROM cal WHERE d < '2026-09-30'
),
dau AS (SELECT event_date, COUNT(DISTINCT user_id) uv FROM events GROUP BY event_date)
SELECT cal.d, COALESCE(dau.uv,0) uv,
       COALESCE(dau.uv,0) - LAG(COALESCE(dau.uv,0)) OVER (ORDER BY cal.d) 环比差
FROM cal LEFT JOIN dau ON dau.event_date = cal.d
ORDER BY cal.d;
09-11  6   0
09-12  0  -6   <-- 补出来了：这天 uv=0，不是"平稳"
09-13  0   0
09-14  7  +7

不做这一步，09-14 会被算成「比 09-11 涨了 1」，看上去平稳； 补上日期维表才知道中间两天是 数据丢了。

D13模板三：漏斗 + 行列转换events + users · 75′
  • 做一张渠道 × 事件层级的透视表：COUNT(DISTINCT CASE WHEN event_type='pay' THEN user_id END)
  • 这就是最朴素的行列转换：把「事件类型」这一列的值，拍平成多个列
  • 再按渠道算支付转化率，找出哪个渠道质量最好
参考答案 + 实测结果
SELECT u.channel,
       COUNT(DISTINCT CASE WHEN e.event_type='visit' THEN e.user_id END) 访问,
       COUNT(DISTINCT CASE WHEN e.event_type='pay'   THEN e.user_id END) 支付
FROM users u LEFT JOIN events e ON e.user_id = u.user_id
GROUP BY u.channel;
投放   访问 6  支付 1
老带新 访问 6  支付 2
自然   访问 5  支付 0   <-- 自然流量看起来免费，实际一个都没转化
