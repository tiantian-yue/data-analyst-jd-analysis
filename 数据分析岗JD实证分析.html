③ 怎么做的

  1. 采集：手机端浏览 BOSS 直聘「数据分析」搜索结果，逐条截图，共 154 张
  2. 识别：本机 OCR（RapidOCR，离线运行，数据不出本机）批量转文字，154 张全部识别成功
  3. 归并：按截图时间顺序合并 —— 有「薪资 + 职位描述」的为首屏（开新 JD），其后无薪资的续屏并入当前 JD
  4. 清洗：剔除 1 张非 JD 页面；修正 OCR 城市错字（「荔州」→「苏州」）；与前期人工采集的 31 条做跨批去重 → 净新增 103 条
  5. 结构化：提取基础字段；技能别名归并（MySQL / 关系型数据库 → SQL，Tableau / PowerBI / 帆软 → BI可视化，SPSS / SAS → 统计学工具族）
  6. 判定：规则引擎判「标题党」（正文无技术技能 + 销售话术特征），每条人工复核。判定标准是「是否挂羊头」，不是「是否提到工具名」 —— 因此某大厂 35-45K 经营分析岗、某通信厂商 10-15K 销售分析岗、某电商数据运营岗虽不写工具名，但职责真实，人工改判为真岗（3 条）。另修正 7 条被 OCR 污染的字段（公司名被地图地址、银行名替换）
  7. 二次去重：改用「正文 4-gram 相似度 + 公司/薪资/城市/经验/学历五字段一致」双重判据，又查出 6 条漏网重复（主因是首轮 2 条记录公司名为空，三重判据失效）
  8. 报告生成：本页所有数字由 scripts/build_report.py 从数据集回算，不手写
去重为什么要人工介入：前期 31 条是人工整理的精简文本，与 OCR 原始噪音文本的字面相似度很低（0.01~0.39）， 自动相似度去重只抓到 1 条。改用多重判据后累计剔除 20 条（首轮跨批 14 + 二轮 6）， 这一步是本次分析里最耗人工的环节，也是最影响结论可信度的环节。

结论 1｜城市能级决定岗位的「真实性」。 太原每 5 条「数据分析」里有 1 条是挂羊头（14/62，95%CI ±10%）； 一线/新一线 64 条里只有 1 条（2%，95%CI ±3%）。 二线城市的数据岗供给里混着大量销售、数据标注、比价录入岗 —— 在一线招「数据分析」基本是真的招数据分析，在二线必须自己筛。
结论 2｜薪资差距约 2.6 倍，且不是「同岗不同价」，而是「根本不是同一种岗」。 太原 5.5K 对应的 JD 通常只要求 Excel + 报表 + 沟通；一线 14.5K 对应的 JD 要求 SQL + Python + 统计学 + BI。 薪资差距的本质是技能要求差距，不是单纯的地域溢价。
结论 3｜SQL 差距是所有技能里唯一已达统计显著的一项（54% vs 81%，+27 个百分点）。 Python 差距 42% → 67%（+25）方向一致但误差带仍重叠，标注为待验证。 想拿一线薪资，补 SQL 的收益最确定 —— 因为 SQL 在一线是「没有不行」。

太原的 AI 岗位呈两极分化 —— 这是本轮最反直觉的发现。 一极是真技术岗：某银行分行 8-10K 明写 PyTorch / TensorFlow；6-11K 数据工程师要求 RAG；6-8K 要求「搭建知识库、智能体」。 另一极是数据标注工：3-4K「AI 训练师」「大模型训练师」，要求本科实则做图片/视频标注 —— 这 2 条已被判为标题党。
所以太原不是没有 AI 需求，而是 AI 需求分化成了「少数真技术岗」和「大量低薪标注岗」。 要避开的是后者。
统计上要说清的边界：太原有 AI 要求 5/48 = 10% （95%CI ±9%），一线 11/63 = 17% （95%CI ±9%）—— 误差带重叠，不能说「太原 AI 要求低于一线」。这里的结论是定性的（两极分化），不是百分比差异。

自采样本是单日快照，回答不了「技能需求怎么变」。所以引入一份第三方公开数据集做对照： 2016-09 拉勾网数据分析岗 589 条（GitHub 公开仓库，含 JD 全文）。 为公平比较，两期都限定为一线城市真实岗位（2016：京沪深广杭 518 条；2026：一线/新一线 63 条）。

1｜涨得最快的是 Python（+48pp）和 BI 可视化（+32pp）。 十年前数据分析岗要求的是「会统计、会报表」，现在要求的是「会写代码、会搭看板」。 SQL 也在涨（53%→81%），但它十年前就已经是主流 —— SQL 是常青树，Python 和 BI 才是增量。
2｜SPSS 是唯一显著崩溃的技能：33% → 6%。 十年前三分之一的数据分析岗点名要 SPSS，现在几乎绝迹。 如果你还在学校被教 SPSS，要意识到它在就业市场已经基本失效 —— 它对应的生态位被 Python 接管了。
3｜Excel 和报表十年没变（40%→33%、51%→59%，均不显著）。 这从时间维度印证了 4.7 节的判断：Excel 是通用办公底子，十年前是、现在也是，因此撑不起溢价。 真正决定薪资的是那几项十年间翻倍的技能。
对照层的口径边界（必须说清）： ①两期来自不同平台（拉勾 vs BOSS直聘）、不同采集方式（第三方爬虫 vs 本人截图 OCR）， 平台差异会混入估计；②2016 年城市只覆盖京沪深广杭，太原仅 1 条，做不了二线的时间对比； ③2016 年 JD 中不存在 AI 要求，该维度无法做时间对比； ④第三方数据未混入主样本，128 条统计口径保持不变。

4.7 三个反直觉的洞察

1｜工具是入场券，业务理解才是溢价。 工具要求密集的岗位集中在 5-13K（SQL + BI + 统计学是标配）；而样本薪资天花板（某大厂 35-45K·15 薪）的 JD 里 一个工具名都没有，只谈经营分析体系、跨部门推动和 PMO。越往上走，JD 越不谈工具。
2｜Excel 是唯一没有「城市溢价」的技能（太原 44% vs 一线 33%，太原反而略高）。 SQL 在一线是 81%、太原 54%；Excel 两地都在 30-45% 区间，且太原需求或不低于一线 —— 说明 Excel 是通用办公底子，撑不起溢价。学习投入应放在有城市落差的 SQL / Python 上。
3｜学历门槛在一线是硬约束，在太原不是。 一线 86% 要求本科；太原仍有 42% 明确接受大专及以下。 对大专学历求职者，二线城市的入口明显更宽；代价是薪资和岗位质量。

⑤ 局限

  • 样本 128 条，但分城市后太原真实岗只有 48 条： 技能占比的 95% 置信区间约 ±13%。因此上表只把 SQL 和标题党比例标为「已显著」， Python / 统计学 / BI / AI 一律标「待验证」——宁可少下一个结论，也不假装一个结论。
  • 非随机采样：来自 BOSS 搜索结果的前若干页，存在平台推荐算法偏差；且太原样本主要来自前期人工采集、一线样本主要来自后期 OCR 批次，两批采集方式不同
  • 自采样本是单日快照：154 张截图全部采集于 2026-10-09，靠它无法观察时间趋势。时间维度改为引入第三方 2016 年数据集做对照（见 4.6），已做城市口径对齐，但两期平台与采集方式不同，趋势结论应理解为「方向」而非「精确幅度」
  • OCR 误差：识别准确率良好但有系统性错字（「职位详情」→「职位洋情」、「苏州」→「荔州」）。城市与公司名靠正则提取，存在误判（7 条公司名被地图地址、银行名替换），已人工核验修正
  • 归并规则是我定义的：「有薪资 + 有描述 = 新 JD」这一假设对连续翻页成立，但若两次浏览同一岗位且中间夹了其他岗位，会算成两条。二次去重补回了 6 条
  • 技能归并表主观：SPSS / SAS 归统计学工具族、Tableau / PowerBI / 帆软归 BI 可视化 —— 换一套规则数字会不同
  • 「标题党」判定含主观成分：规则初判 + 全部人工复核，仍保留判断空间
  • 社保/双休维度覆盖率仅约 5%：首轮多数截图未滚到页面底部（仅 25% 截到「立即沟通」标记处）， 该维度本轮不足以支撑结论，已如实标注为缺失，第二轮采集已修正截图规范
  • 薪资是招聘方标注区间，非实际成交价，区间中值不等于实际 offer
